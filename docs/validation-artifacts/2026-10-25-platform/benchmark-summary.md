# 平台本地 CPU / I/O 对照（2026-10-25）

同一 Mac、同一个项目 Python 3.12.10、FFmpeg 8.1.1。基线为 `2fb6a4d` 的 `git archive`，当前版本为本轮未提交工作树。每项先暖机一次，再顺序测三次，给出中位数和范围。测试期间项目其他实施仍在进行，因此这些数字用于定位量级，不代表隔离硬件环境中的发布基准。无 GPU、真实转录吞吐或准确率数据。

## 解码与归一化

44.1 kHz 双声道合成 WAV 转 16 kHz 单声道 PCM16；两版输入 SHA-256、输出 PCM SHA-256、帧数及声道一致。新 WAV 头由服务补齐（44 bytes），基线 FFmpeg 容器头为 78 bytes；文件整体摘要不同不代表音频采样不同。

| 原音长度 | 旧解码：中位 / 范围 ms | 新解码：中位 / 范围 ms |
| --- | --- | --- |
| 30 s | 55.796 / 55.780–56.075 | 53.792 / 49.196–53.968 |
| 180 s | 112.276 / 109.715–113.103 | 103.721 / 102.540–301.432 |

这些短样本不能证明解码总耗时显著下降。工作台原流程会先生成 audio.wav，quality 再生成 normalized.wav；本轮通过可信资产借用消除第二次归一化。正常重试从经规格/帧数/摘要验证的资产恢复。归一化调用次数属于行为验收，不能把少一次复制直接换算为真实 ASR 端到端提速。

## 日志压力

最终保留策略版本见 `current-final-logs.json`；`current-cpu.json` 的早期日志部分已被它替代。固定 10,000 次事件调用、4096 槽队列，生产者尽快提交，用于检验拥塞有界；没有混入人为推理耗时。

INFO 生产者中位 64.673 ms，关闭 INFO 的中位 0.771 ms；每次额外约 6.390 µs，相对生产者开销 8287.8%。三次丢弃 [6024, 6023, 6024] 条，队列持续有界。INFO 含清空队列总耗时范围 98.992–101.847 ms。

这项 hot loop 不能代表计划中的完整固定转录负载开销目标。随后另做 GPU 同负载 INFO/CRITICAL 各三轮对照，见 [WSL 记录](../../validation-2026-10-25-wsl-platform.md)；小样本仍不能保证稳定低于 3%。事件丢弃计数保留在 API 内部统计及后续事件中。

## 混合 ASGI 控制面负载

同一个 Python、两版源码独立进程顺序执行。每轮 1000 条含 16 KiB 合成文字的任务，10 个已登录客户端每 3.5 秒分别请求 health 和个人列表，共三次轮询；后台两个上传各 1,920,044 bytes 有效 WAV，加一个持续 8 秒的 mock 推理任务。每轮测量约 7.1 秒，额外等待推理安全完成后再关停；三轮均观察到 transcribing 并最终 completed。每轮先为每客户端暖机一次 health 和列表。

旧列表返回 1000 条；新列表使用 summary 50 条。每轮 health 30 次、列表 30 次，三轮合计各 90 次。未通过网络套接字，不测 LAN/TLS/浏览器/GPU；20 ms timer 的 loop lag、计划发送时刻偏差均单独记录。当前版运行前等最终 pytest 完成，未与本项目其他 CPU 压测并行。

| 轮次 | 旧 / 新列表 p95 ms | 旧 / 新 health p95 ms | 旧 / 新 loop lag p95 ms | 旧 / 新 loop lag max ms |
| --- | --- | --- | --- | --- |
| 1 | 194.277 / 33.528 | 1.786 / 1.143 | 2.162 / 2.169 | 186.656 / 16.866 |
| 2 | 189.424 / 33.815 | 2.258 / 2.117 | 2.198 / 2.175 | 179.598 / 11.800 |
| 3 | 189.899 / 35.580 | 0.417 / 0.946 | 2.112 / 2.153 | 192.794 / 11.778 |

三轮列表响应总量：旧 30,510,900 bytes，新 2,243,520 bytes。每轮实际墙钟、上传耗时、响应字节、采样数和延迟范围均保存在 `baseline-latency.json` / `current-latency.json`。

本合成 ASGI 场景中新列表 p95 低于 100 ms、loop lag p95 低于 50 ms；旧版 loop lag 的 p95 也很低，但存在约 180–193 ms 的少量阻塞尖峰。不能用 p95 掩盖这些最大值，也不能把本场景结果推广为真实 GPU 并行或 LAN 延迟承诺。

## 复现与证据

完整命令、基线完整 commit、原始指标文件 SHA-256 见 `measurement-manifest.json`。脚本位于 `scripts/platform_benchmark.py`，`--source` 必须指向要测量的代码树；基线与当前使用独立进程。scratch、output 参数必须是新路径；脚本会移除自身创建的合成数据库、音频和日志目录。原始 JSON 保留每次采样、机器及缓存说明。

本文件只描述本地 CPU/mock。真实模型 RTF、显存、切换和预取另见 [WSL 记录](../../validation-2026-10-25-wsl-platform.md)；六小时完整网关 RSS 已补测，见下节。实际 LAN＋GPU 混合负载 p95/loop lag 及人工识别质量仍未验收。
