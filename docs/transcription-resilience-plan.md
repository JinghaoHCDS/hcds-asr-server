# 转录健壮性与高可用专项修复计划

日期：2026-10-26。状态：健壮性功能已实现并上线，专项尚未关闭；实测与未验收项见[验收记录](validation-2026-10-26-transcription-resilience.md)。两条任务均已处理到末尾，保留四处未分类声音待回听，不能称为已确认漏字。基线为 `c87eee2` 的 schema 4、持久 MP3、单 GPU FIFO 和 `quality_v1.4`。本文结合本次会话的线上复现与当前源码检查制定；尚未进行的故障注入、时限和质量验收单独列出。

目标是让偶发识别异常能够有界恢复，局部困难音频不阻塞后续内容，进程故障后能保住已完成进度，并让用户清楚知道任务停在哪里、是否还会自动恢复。

## 1. 范围与完成定义

本轮在现有 Windows / WSL、单 GPU、单服务实例上加强故障恢复。保留唯一 LAN 端口 `18080`、现有模型及能力发现、账户隔离、MP3 保存方式和终态七天保留规则。优先让查看文字、回听、导出和取消在推理故障期间继续可用。

单机能够做到进程拉起、任务恢复和推理故障隔离；整台主机、磁盘或网络不可用期间，仍存在服务中断。备用主机、跨机数据复制、故障接管属于后续独立建设，本轮不宣称双机高可用或承诺未经测量的可用率。

接口边界：工作台 `/api/**` 承担持久恢复和部分结果交付；`/v1/**` 保持默认 `legacy`、原同步响应及内存 job 语义，不承诺服务重启后恢复已丢失的临时输入。显式选用 `quality_v1` 的调用共享受版本约束的质量策略，worker 隔离与就绪检测则惠及所有入口。MOSS 保留自身识别、生成预算和说话人策略，只接入通用故障治理。

本轮结束须同时满足：

1. 两条已知失败任务在保留原有检查点的情况下完成恢复；所有新增恢复片段都有来源、实际调用参数和质量检查记录。
2. 确实无法识别的区间显式保留缺口；其他区间能继续处理、查看和保存，缺口不会被包装成完整成功。
3. 可恢复的 worker 故障有界自愈；单个坏任务和重复崩溃不会持续占住 GPU 或拖垮队列。
4. 已持久确认的片段在受测重启场景中不丢失、不重复发布；取消、删除和编辑版本不被晚到结果覆盖。
5. 上线、回滚、任务恢复及关键故障注入有可复现记录，前端能显示具体原因和下一步动作。

## 3. 修复主线一：识别异常的有界恢复

### 3.1 按故障原因选择动作

| 故障 | 自动动作 | 停止条件 / 用户动作 |
| --- | --- | --- |
| auto 空稿，有一致的语言依据 | 尝试一次显式语言识别，保留原稿和恢复来源 | 没有可靠语言依据时只走分段复核；仍失败则标记缺口 |
| 空稿且有独立无语音证据 | 按现有严格证据规则接受空段，保留待复核标记 | 检出语音、检测不可用或异常时不得按静音放行 |
| 生成截断、循环重复、边界异常 | 缩短窗口复核，逐个检查子结果 | 到达尝试数或总预算上限后记录未解决原因 |
| worker 超时、退出、Pipe 关闭、可恢复 CUDA 故障 | 确认旧进程退出，重建 worker，按任务恢复规则再次排队 | 持续失败触发熔断；不无限重启，不自动换模型或降质量 |
| 对齐失败 | 保存已经获得的原始转录；仅重试对齐 | 字幕保持不可用/待完成，文字仍可查看 |
| 音频损坏、身份冲突、参数无效、权限问题 | 明确失败并保留已有证据 | 修复输入或由用户明确选择从头处理，不自动消耗 GPU 重试 |
| 空间不足、DB 不可写、资源额度不足 | 停止新写入和相关准入，保留已有文件 | 空间/存储恢复后再继续，不删除未到期用户数据腾空间 |
| 用户取消或删除 | 按现有安全边界停止并清理 | 不进入任何自动恢复流程 |

### 3.2 语言恢复必须有依据

- 仅对原请求 `language=auto` 且确实空稿的 Qwen 片段启用；显式指定语言的任务尊重原请求。
- 初版候选规则：前面最近三个已确认的非空片段，模型语言标记一致、合计至少 30 秒，且没有已知混合语言或语言冲突信号，才允许选择该语言。该规则是待验收的保守启发式，不把模型标签当作独立语言真值。
- 首段、证据不足、语言变化或混说无法排除时，不自动强制中文；走边界复核并留下可回听区间。记录所用片段索引和语言依据，以便复现。
- 回退只覆盖本次调用的有效语言参数，原始请求、词库快照和幂等身份保持不变；记录 `requested_language`、`effective_language`、策略版本和触发原因。
- 恢复候选检查截断、重复、子段完整覆盖、文字与真实对齐关系及明显未覆盖的语音区；保留 `language_fallback` 待复核标记。非空文本或对齐成功均不能单独作为质量通过依据。
- 修复前先保留最小输入、提示结构、模型及处理器版本的复现证据。若要修改正常 auto 提示路径，作为独立基线升级验收，不能隐藏在恢复策略中。

### 3.3 修正拆段提前退出

子段遇到空稿或截断后，记录该子段的结果并继续处理同一复核轮次的其余子段。系统错误、取消、删除、额度耗尽仍立即停止对应操作。

每个子段都有明确的时间范围、调用状态及结果。全部子段得到有效文字或符合严格空段证据后，才能将父块记为已解决。不能用已成功子段的拼接文字掩盖失败子段；不能只检查最后一个子段的 `generation.truncated`。

先保留已有完整覆盖切分，不在本轮同时更换切分器或默认 chunk 时长。按采样边界组织子段，字幕时间来自真实对齐，chunk 边界只用于标识处理范围。

### 3.4 统一恢复预算

新增一个统一的策略调度入口，避免 pipeline、adapter、任务重试各自循环而相互放大。

- 建议每个原始 chunk 最多执行三个质量恢复动作：一次有依据的显式语言尝试、一次二分复核、一次四分复核；每种动作最多一次。子段不递归启动一套新的额度。
- 这会将现行“最多两轮复核”明确扩展为“最多两次重新切分加一次语言恢复”。实施时同步产品契约与运行文档，不能只改代码。
- 总质量复核音频预算仍不超过首次输入时长的 30%。同一声音被重复送入模型时分别计费；二分/四分一次合计按父块时长预扣，未执行完的部分保守不退还，兼容现有账本。
- 短音频可能连一次整块恢复的预算也不够，必须在验收中覆盖并显示“自动复核额度不足”；不能为了让恢复样例通过而暗中突破 30%。若后续需要保证短音频至少恢复一次，应作为单独的预算契约变更评估成本。
- 原始失败调用也要持久标记已发生；普通重试不能每次免费重跑同一个确定性空稿调用。新策略或确有变化的运行条件才能产生下一次有效动作。
- worker 故障恢复单独记录基础设施尝试：建议每个操作最多一次自动重新执行，任务累计最多三次；进程崩溃也不能清零。若发生在质量复核调用中，重复音频仍计入质量预算。
- 现有生命周期层的“一次非 fatal 重试”纳入同一尝试记录，禁止再在外围叠加一次隐藏重试。CPU 检测另外记录耗时并受 deadline 约束。
- 先持久预扣、再发起调用；中断后不能退回“未尝试”。任务普通重试、自动恢复、服务重启都继承账本；策略版本升级不自动赠送无限额度。

## 4. 修复主线二：保住进度，支持带缺口的恢复

### 4.1 当前两条任务的兼容处理

当前保留的是 schema 4 MP3 任务，本轮必须原位保留；上次音频改造的旧任务清理流程不适用于此次发布，禁止调用 `workbench_reset_tasks` 或批量从头重试。

保留原有基础执行身份，新增独立的 `recovery_policy_version`。仅当模型、处理器、基础推理、切分、音频解码和冻结请求均未改变时，才允许在相同基础结果上附加恢复策略。不能仅为了复用检查点而保持一个实际上已经失真的版本号。

实施时为旧任务提供显式、可审计的兼容导入：

1. 校验 MP3 摘要、重建 PCM 摘要、解码规范、模型/aligner/detector 身份、冻结参数及词库、完整 chunk 列表和原指纹。
2. 对已完成的 36 / 19 个检查点保存摘要清单；这些内容不重写、不重复识别。已完成的 JYQX1 结果保持原样。
3. 原两次拆段尝试及已耗时长原值导入；仅开放新策略中的一次语言恢复动作，并继续受原任务 30% 总预算约束。
4. 新恢复记录放在独立版本空间，绑定原始基础指纹、chunk/子段范围、语言依据、实际参数和尝试 ID。新程序通过明确的兼容读取器组合结果；旧程序不得把新结果当作原策略产物。
5. 身份不一致或剩余额度不足时返回具体原因，提供保留进度的查看/导出；从头运行必须是显式用户动作。

新任务使用完整的新执行清单。若修改了正常推理路径、输出语义或默认参数，必须更新基础流程身份，并通过明确的迁移规则处理旧任务，不能覆盖 `identity.json` 绕过检查。

### 4.2 区间结果与完整性

以稳定的 `chunk_index + start_sample + end_sample` 标识处理单元，保存 `resolved`、`empty_with_evidence`、`unresolved` 及对齐状态。完成计数来自已经持久提交的有效区间；`attempted` 与 `resolved` 分开统计。

质量恢复耗尽后，将该区间登记为缺口，继续处理后续原始块。基础设施或存储故障仍暂停整条任务。后续正常结果按原始位置持久化，重试只处理未解决区间；不要求所有有效检查点必须构成连续前缀。

第一版保留既有任务状态枚举：全部处理结束但仍有缺口时保持 `failed` / `quality_incomplete`，同时提供部分结果、完整性字段和缺口清单；全部区间通过后才为 `completed`。质量待复核标记单独保留，不以状态完成暗示文字已获人工确认。

部分 TXT / JSON 导出必须标明“不完整”及缺口时间；字幕导出默认要求对应范围具有有效真实时间，不能填造缺口字幕或插入占位词冒充识别文字。显示“已解决 70 / 73 段，3 个区间待处理”比单一失败标签更可用。

为避免每个坏区间重新触发一轮全任务扫描，合并与最终检查只读取区间清单；对既有成功片段不重复推理。编辑、部分结果与最终版本均保留 revision，恢复不能覆盖用户后续修改。

### 4.3 转录和对齐分开落盘

在适配器内部取得原始文字后先形成可恢复的转录产物，再进行对齐。对齐失败时保存原稿和原因，下一次仅恢复对齐。初版保持同一个调度操作串行执行，避免顺带改变 FIFO 公平性。

这一步需要调整 Qwen 当前“转录加对齐一次返回”的内部接口，不能只在前端把错误换成成功。对齐不可用时可查看原稿，涉及真实时间戳的质量检查继续待完成；字幕不可用的状态必须准确。

### 4.4 跨文件与数据库的一致性

- 为每次执行分配持久 `attempt_id` / generation；结果提交使用条件更新，确认任务没有取消、删除、版本变化或被新尝试接管。保留当前单进程文件锁，避免两个服务实例同时恢复同一数据目录。
- 检查点文件写入、文件 fsync、原子重命名、目录 fsync 完成后，才提交数据库可见索引和进度。数据库事务失败时重启核对文件与索引，不重复发布成功块。
- 对“文件已写 DB 未提交”“DB 已确认文件缺失/损坏”“预算已预扣结果未写”分别设计恢复路径。只隔离损坏任务/区间；整个 DB 不可写时关闭写准入。
- schema 4 如需升级，使用保留全部任务的事务迁移；既有“非空旧库需要清空”的升级守卫不能直接沿用。迁移须幂等、可备份恢复，并有新旧版本兼容测试。
- 重启不重新计算任务创建时间、不复活已删除任务、不自动续期终态保留期；只有真实进入新一轮处理并完成时才按现行契约写终态时间。

## 5. 修复主线三：单机服务自愈与降级

### 5.1 分阶段 deadline 与异常 worker 隔离

保留现有进程隔离和超时回收，补上模型加载、单 chunk 识别、对齐和 native long-form 的独立 deadline。阈值用目标 WSL 上的实测耗时、高 token 上限和最长允许输入制定；不能把 Qwen 短片段的超时直接套到 MOSS 长调用。

先用候选配置观测，再启用自动中止。预期是将短片段卡死从默认最长一小时等待缩短到有实测依据的范围，同时给冷加载和重型调用保留余量。正常推理不因 UI 百分比未变化或短暂 GPU 利用率下降被中断。

超时或协议故障触发：标记该 generation 不可用 → 回收旧进程 → 确认 PID 退出及通信关闭 → 释放调用所有权 → 有界重建。旧进程未确认回收时保持 GPU 隔离状态，拒绝新 GPU 调用；不能只打日志然后启动第二个 worker。

取消保持“当前健康调用安全结束后停止”的语义；只有硬 deadline、fatal worker 或服务关停到达既定上限才按故障路径终止子进程。

### 5.2 持久重试、退避与熔断

- 基础设施故障清理结束后写入 `retry_wait` 阶段和 `next_attempt_at`，释放调度槽位；倒计时期间不持有 GPU、不阻塞其他任务。
- 同一任务退避建议从 5 秒起，后续全任务故障间隔逐步增长并设置上限；确切参数作为配置和验收结果发布。自动重试次数按上一节持久限制。
- 到期重试作为新一次调度提交进入现有 FIFO，不插到旧队列前，也不改按模型分组。持久保存提交次序，重启恢复遵守同一顺序；现有首次提交 FIFO 契约保持。
- 以模型/worker 为单位记录故障窗口，建议连续三次 fatal 故障触发 60 秒冷却。冷却后仅放行一个受控恢复尝试，其余请求显示等待服务恢复；真实成功才关闭熔断。
- GPU 全局不可用、进程无法回收等共因故障使用全局熔断；普通识别空稿不会导致模型熔断。没有必要时不新增独立推理“探针任务”。
- 同一失败不能在适配器、任务队列和 systemd 三层各自无限重试。超过上限转为可解释失败，保留音频、结果和诊断；用户点击重试也不清空质量预算。

### 5.3 存活、就绪与降级

保留 `/health` 的现有兼容行为，新增轻量 `/readyz`，表示能否接受新的推理操作，200 为可接单、503 为暂不可接单。只公开总体状态和有限原因，不暴露任务、路径或账号；详细状态放在管理员接口。

就绪判断检查调度循环、数据可写性、必要资源、维护/排空状态和熔断状态。模型正常 unloaded 不等于服务故障，正常冷加载也不触发重启；GPU 快照过期表示检测信息不足，不能单凭它宣称 CUDA 已坏。

正常队列满沿用 `429 job_queue_full` 和容量准入，不触发进程重启；持续无法执行与正常排队等待分别呈现。自动恢复所需字段在任务摘要里有界返回，轮询不能重新读取全文或扫描音频目录。

推理就绪与数据服务可用性分开：worker 熔断时仍允许登录、读取已有任务、回听、导出和取消；新推理返回明确的暂不可用与重试提示。上传只在持久容量和受控积压额度允许时继续接受。

增加后台监督：单轮清理/补队列失败应记录、退避并继续；维护不能永久退出。调度循环异常先确认无活跃调用和残留 owner 才重建；无法证明安全时关闭推理准入并进入可诊断状态。监督循环不得因为长模型调用就认为调度已死。

systemd 保留 `Restart=on-failure`，补充重启频率限制及与应用关停上限匹配的配置。网关卡死检测要独立于被监测的事件循环；仅在事件循环持续失联且达到阈值时触发进程级恢复，不因推理变慢重启整站。

### 5.4 发布排空与恢复

为发布提供显式排空状态：拒绝新增推理及提交，允许现有任务在安全 chunk 边界保存后进入可恢复等待；完成中的编辑和文件提交也要纳入排空。仍保留查看和回听。

排空结束、确认无活跃消费者后停止服务，使用一致的 SQLite 备份和音频/检查点清单安装新版本。恢复时先核对数据和任务，再开放新准入；部署成功判断包括 `/readyz`、队列可执行性和真实转录，不能只看 `/health` 返回 200。

本轮不自动改变 Windows 电源策略、WSL 启动策略或防火墙。可使用已有启动方式完成恢复验收；若要实现 Windows 重启后无人值守启动，再将具体宿主配置列为独立交付和实机验证项。

## 6. 用户界面与诊断

用户看到的应是当前情况及可操作动作：

| 情况 | 显示内容 | 动作 |
| --- | --- | --- |
| 正在自动复核 | 正在复核第 N 段，区间时间，已完成数量 | 回听、取消 |
| worker 恢复等待 | 服务正在恢复，已保存进度，下次尝试时间 | 查看已完成文字、取消 |
| 仍有缺口 | 已解决 / 总段数，未解决区间和简短原因 | 跳转回听、恢复未完成区间、导出部分结果 |
| 原参数已无可用恢复动作 | 具体说明已尝试方式和停止原因 | 回听；如提供新语言/参数则显式建立新处理版本 |
| 身份不兼容 | 旧进度可查看，说明哪个身份变动 | 用户明确选择从头处理 |
| 只有字幕失败 | 原稿可用，字幕未完成 | 重试对齐、导出 TXT / JSON |

重试动作由后端 `retryability` / `next_action` 决定，前端不能仅按错误码拼出一个永远有效的“重试”。按钮防重复、请求幂等、跨用户归属检查继续保留。新增字段通过 OpenAPI、官方 Skill/客户端所涉及的接口同步说明。

诊断沿用 JSONL 关联体系，增加策略版本、chunk/子段、attempt、基础/有效语言、预算变化、失败原因、worker generation、下一次恢复时间和结果完整性。默认不记录正文、完整 prompt、音频、凭据；语言依据只记索引和标签。

管理员摘要显示：分类失败数、恢复成功数/尝试数、质量缺口数、最老排队时长、worker 故障/熔断、当前阶段耗时、重启恢复耗时、磁盘余量和清理失败。指标明确统计窗口及分母；一次 smoke 不能替代长期可用率。日志仍按现有容量和隐私边界执行。

## 7. 实施顺序与交付关口

| 阶段 | 工作 | 交付与通过条件 |
| --- | --- | --- |
| P0：解决本次故障 | 最小复现；语言恢复；拆段完整检查；统一质量账本；旧任务兼容读取；最小失败区间提示 | 两个真实失败区间得到经检查的恢复结果；保留旧块从失败点继续，两条完整任务最终无未解决缺口。未达成不得宣称本次故障已修好 |
| P1：任务健壮性 | 稀疏区间与部分结果；转录/对齐分别落盘；提交 fencing；保留数据迁移；持久基础设施重试 | 从上传到结果跑通一次完整真实流程；故障/重启后成功块不重做，缺口可恢复，取消删除不复活 |
| P2：服务自愈 | 阶段 deadline；无法回收的 worker 隔离；退避/熔断；readyz；维护监督；发布排空 | 故障任务不会无限占队列；后续健康任务可完成；网关读取功能在推理故障期间可用 |
| P3：发布验收 | 质量集对照、故障演练、持续运行、界面、自检工具、运维说明 | 验收矩阵通过，源码与线上版本可核对，已知限制写入验收记录，完成部署后再推远端 |

先完成一条“空稿 → 有依据恢复 → 原检查点续跑 → 真实对齐 → 工作台可查看”的纵向流程，再扩展故障覆盖。P0 可作为独立修复发布，但整个专项需完成 P1–P3 才关闭。

主要代码责任范围：质量逻辑在 `quality/` 和 Qwen adapter；恢复/状态/迁移在 `workbench/`；worker 与队列可用性在 `workers/transport.py`、`lifecycle.py`、`scheduler.py`、`main.py`、`config.py` 和部署模板；界面在 `App.tsx`、`ResultPane.tsx`、`AdminPane.tsx`、`api.ts`。新模块只在能明确隔离恢复策略和持久状态时增加。

## 8. 验收矩阵与指标

所有新增时间指标均为拟定验收目标，尚未测得。Mac 负责确定性逻辑和故障模拟；真实 CUDA、模型、对齐和进程资源回收在已授权 WSL 范围内验证。破坏性故障注入使用独立数据目录和自有测试任务，按 GPU 空闲窗口运行，不对用户正在处理的任务直接 kill。

| 验收组 | 样本 / 注入位置 | 必须观察到的结果 |
| --- | --- | --- |
| 本次复现 | MM1、JYQX2 失败区间及整条续跑 | 原检查点摘要不变；新策略有来源；任务无静默遗漏；已完成 JYQX1 不变 |
| 语言与空段 | 中文、英文、中英混说、语言切换、开头无语言依据、静音、音乐、低音量、音乐后讲话 | 无依据不强制语言；有声空稿不被放过；独立证据不可用时不放宽静音门槛 |
| 拆段与质量 | 首子段失败但后子段有声；中间失败；某子段截断；循环重复 | 检查全部必要子段；局部失败不伪装父块完成；预算准确、不会递归放大 |
| 预算恢复 | 调用前预扣后崩溃、重复点击、重启、旧两次尝试已用完 | 尝试和预算不回退；旧额度完整继承；耗尽后停止自动调用 |
| 检查点一致性 | rename 前/后、DB commit 前/后、坏 JSON、摘要不一致、缺失文件 | 只重做未确认部分；不能混入错误身份；无半块、重复正文或假进度 |
| 稀疏结果 | 前段失败、后段成功后重启；只恢复缺口 | 保存和重用后续成功块；顺序正确；缺口可见；部分导出明确不完整 |
| 对齐恢复 | ASR 已得文字后 aligner 失败或退出 | 原稿仍可恢复；只重跑对齐；字幕不使用假时间 |
| worker 故障 | EOF、异常退出、RPC 超时、CUDA OOM、协议错、回收失败 | 有界恢复；旧进程未回收不新开 GPU worker；随后健康任务不被无限阻塞 |
| 队列与取消 | 混合同步/旧 job/工作台/编辑；恢复等待中取消；删除时返回晚到结果 | 单 GPU 串行、重试按新序号入队；取消删除最终生效；文件和额度释放一次 |
| 服务重启 | 安全退出与强制退出；连续重启；维护异常；队列循环异常 | 持久任务恢复，失败循环受限；就绪状态准确；内存 job 仍按原契约失效 |
| 存储异常 | ENOSPC、SQLite busy/不可写、清理失败、账本与磁盘不一致 | 不发布不可恢复成功；保留唯一有效音频；阻断相关写准入；恢复后可继续 |
| 界面与隔离 | 桌面/手机；断网重连；普通/管理员/另一用户 | 原因和动作清晰，回听定位正确，部分结果可用，状态刷新及时，无跨用户内容泄漏 |
| 发布与回滚 | 新旧源码、前端、schema、策略记录组合 | 不清空现有任务；不静默降级读新格式；可恢复匹配的代码与数据 |

工程指标：

- 在本轮受测进程崩溃场景中，已向客户端确认持久完成的 chunk 丢失数为 0；未确认调用允许重做。硬盘损坏和宿主掉电不由这项指标自动覆盖。
- 每个质量动作和基础设施恢复都不超过持久上限；注入永久故障后最终进入明确停止或熔断状态，不能持续忙重试。
- worker 硬故障后的恢复用“检测耗时 + 回收上限 + 退避 + 真实加载耗时 + FIFO 等待”分别报告；不能将一个固定秒数误称为所有模型的恢复承诺。
- 推理故障但 DB 正常时，已有任务查询、回听、结果导出可用；目标环境正常负载下轻量查询 p95 目标小于 500 ms，报告并发数、数据规模、缓存状态和测量方法。
- 重启恢复单独测量网关就绪和首个可执行任务开始的时间，冷加载单列；初始网关目标为 60 秒以内，按本次实际数据规模验证，不作为任意数据量承诺。
- 完成、失败、取消和恢复等待退出后没有无主 PCM、分片或未结算 lease；持续运行至少 8 小时验证资源回到合理基线，无单调累积的泄漏。

质量验收分开发集和独立验收集。两个失败区间用于开发，不兼作全部验收证据；至少加入上述声学/语言条件的独立样本和人工参考文本，比较 CER、漏词、幻觉、重复及字幕偏移。正常已通过样本出现新增整段遗漏或明显虚构即阻断发布；其他退化逐条说明并处理，不用总体平均值掩盖。

最长六小时需要至少一条实际长输入完成工程验证，报告真实耗时、内存/显存/磁盘峰值和恢复行为。合成循环音频只证明资源边界；没有真实长素材和人工参考时，六小时质量仍标为未验收。若当前缺少独立样本或参考文本，在 P0 完成后列明具体缺口，不把相同开发片段的重复测试当作质量放行依据。

## 9. 上线、回滚与证据交付

1. 冻结复现信息和现有任务清单；保存音频/检查点/结果/账本摘要，不把私人素材或正文加入 Git。
2. 在本地完成相称的行为测试、类型检查和前端构建，复用现有测试入口；新增测试集中在恢复决策、数据一致性及故障后行为，不为实现细节写镜像断言。
3. WSL 隔离数据目录执行实际模型与故障演练，先完成一个真实端到端流程，再运行验收矩阵和长时测试。
4. 排空、停服务并备份源码、前端、SQLite、MP3、检查点和相关版本；备份清单与恢复程序必须匹配。升级绝不执行上一轮旧任务清空流程。
5. 部署后检查服务、就绪、登录、队列、Range 206、部分/完整导出和容量账目；再以有日志记录的恢复操作处理两条失败任务，检查原有成功块不变。
6. 验收通过后写 `validation-YYYY-MM-DD-transcription-resilience.md`，保存去敏的指标及诊断 JSON，核对线上源码摘要/发布版本，提交聚焦改动并推远端。

回滚应优先关闭新恢复策略并继续读取已有新格式数据。若必须回退旧代码，停止写入后先保存新版本运行期间产生的全部数据，再按已验证的兼容路径或配套快照恢复；不得用旧备份静默覆盖上线后的上传、编辑和新结果。旧程序不认识新格式时明确拒绝启动，不绕过版本守卫。
